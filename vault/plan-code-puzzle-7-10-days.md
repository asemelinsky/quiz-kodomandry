# Code-puzzle — план курсу 8-10 днів

**Адресат:** founder Кодомандри (Олексій Семелінський)
**Автор:** methodist (Claude, з quiz/ background)
**Дата:** 2026-06-15
**Контекст:** оцінка чи можна утримати дитину 8-10 років чисто логічними задачами без 2D-сцени. Парний документ до [`2026-06-14-code-puzzle-track-concept.md`](https://bajka.pp.ua/notes/phase0/reports/2026-06-14-code-puzzle-track-concept/).

**Обмеження:** Phase 0 cognitive-load invariants ([`cognitive-load-invariants.md`](https://bajka.pp.ua/notes/phase0/methodology/cognitive-load-invariants/)) — макс 1 overlay, ≤5с time-to-action, TTS chunk 5-15 слів, click-to-feedback <500мс.

**Принципи каркасу** (взято з [`blocks-program.md`](https://bajka.pp.ua/notes/phase0/methodology/blocks-program/) для Module 1, адаптовано): нова концепція не частіше ніж раз на 1-2 дні, обов'язкові 🔁 consolidation-дні, фінал з композицією.

## 1. Огляд програми (10 днів)

| День | Тема | Тип | Нові блоки | Концепція | Output type | Чому це цікаво 8-10 |
|---|---|---|---|---|---|---|
| 1 | Перший вивід | 🆕 | `[число]`, `[вивести]` | Sequence: програма має початок і дає результат | число | Перший момент агентності — «я кажу комп'ютеру що показати» |
| 2 | Обчислення | 🆕 | `[+] [−] [×] [÷]` | Композиція операцій | число | Знайома з школи арифметика, але вони її БУДУЮТЬ, не розв'язують |
| 3 | Порядок дій | 🔁 | — | Вкладеність, пріоритет | число | «Math trick» — `(2+3)×4` vs `2+(3×4)` дає різні результати |
| 4 | Цикл `repeat` | 🆕 | `[repeat N]`, `[вивести ⭐]` | Повторення без копіювання | патерн з ⭐ | Драматичне стиснення — 10 копій блоків → 1 цикл. Емоційна перемога. |
| 5 | Змінна + лічильник | 🆕 | `[set x = ?]`, `[x]`, `[change x by ?]` | Пам'ять у програмі | список чисел | Шкільна змінна (`a=2`) тут ОЖИВАЄ і змінюється протягом програми |
| 6 | Візерунки | 🔁 | — | Synthesis repeat + var | таблиця, трикутник | Фібоначчі, таблиця множення, ⭐-трикутник — естетика результату |
| 7 | Перші умови `if` | 🆕 | `[if (...) then (...)]`, `[>] [<] [=]` | Branching: програма приймає рішення | відфільтрований список | Знайоме «якщо-то» з життя, тут формалізоване. FizzBuzz light. |
| 8 | `if-else` + AND/OR/NOT | 🆕 | `[else]`, `[AND] [OR] [NOT]` | Повна булева логіка | true/false, FizzBuzz | Truth-tables, повний FizzBuzz, mystery: «що виведе ця програма?» |
| 9 | Процедури | 🆕 | `[define block "..."]`, `[call "..."]`, `[parameter]` | Створення власних блоків | reuse, recursion | Метакогніція — «я роблю свій інструмент», базова рекурсія для готових |
| 10 | Фінал: міні-app | 🏆 | — | Композиція всього | mini-application | Спроба «справжнього коду» — калькулятор, прогноз-гра, лотерея |

**Розподіл нових концепцій:** 1 на день з 6 «нових» днів (1, 2, 4, 5, 7, 8, 9), що відповідає invariant'у Phase 0 «не більше 1 нової концепції/день». Дні 3, 6 — consolidation. День 10 — finale.

**Темп ускладнення в кодовому виразі:**
- Day 1-3: програми 1-3 блоки, лінійна послідовність
- Day 4-6: програми 3-7 блоків, петля + стан
- Day 7-8: програми 5-12 блоків, розгалуження
- Day 9-10: програми 10-20 блоків з власними процедурами

## 2. Як використовувати ЦИКЛИ без візуальної сцени

**Ключ:** output має «накопичуватись» візуально, щоб emerging pattern давав той самий dopamine, що рух Pixel-а на сцені.

### Приклад типу задачі А — естетичні патерни через emit

```
Задача: «Намалюй ⭐-трикутник»

Очікуваний output:
⭐
⭐⭐
⭐⭐⭐
⭐⭐⭐⭐
⭐⭐⭐⭐⭐

Доступні блоки: [repeat N], [вивести [рядок]], [число], [+], [x], [set x = ?]

Рішення (одне з):
set x = 0
repeat 5 times
  change x by 1
  вивести (⭐ × x)   ← string multiply
```

Дитина бачить як трикутник з'являється рядок за рядком у Result box. Visceral reward — без жодного персонажа.

### Приклад типу задачі Б — числові послідовності

```
Задача: «Виведи перші 10 квадратів натуральних чисел»

Очікуваний output: 1, 4, 9, 16, 25, 36, 49, 64, 81, 100

Доступні блоки: [repeat], [set x], [change x by ?], [×], [вивести]
```

Висновок на екрані з'являється послідовно — fade-in кожне нове число з мінімальною анімацією (200мс fade). Тут important UI tweak: **не дамп одразу всього списку — поява по одному з тиком 100-200мс** — це і є наша заміна анімації Pixel-а.

### Приклад типу задачі В — constraint puzzle

```
Задача: «Виведи рядок з 12 ⭐, але repeat може бути ТІЛЬКИ зі значенням 3 або 4»

Рішення вимагає: 3 × 4 = 12 → nested repeat
repeat 3 times
  repeat 4 times
    вивести ⭐
```

Це чисто інтелектуальна головоломка. Награда — «знайшов!» momentum. Працює для 8-10 коли є visible progress meter (скільки ⭐ ще треба).

## 3. Як використовувати УМОВИ без візуальної сцени

### Приклад типу задачі А — фільтр по списку

```
Задача: «Виведи всі числа від 1 до 20 які діляться на 3»

Очікуваний output: 3, 6, 9, 12, 15, 18

Доступні блоки: [repeat], [set x], [change x by ?], [if (x % 3 = 0)], [вивести]
```

Емоційна точка: дитина запускає, очікує побачити просто 1-20, але бачить ВІДФІЛЬТРОВАНУ підмножину. «О, програма виокремлює!» — це і є моменти insight без stage.

### Приклад типу задачі Б — FizzBuzz light (Day 7)

```
Задача: «Виведи числа 1-15 але замість тих що діляться на 5 — пиши '⭐'»

Output: 1, 2, 3, 4, ⭐, 6, 7, 8, 9, ⭐, 11, 12, 13, 14, ⭐

Блоки: [repeat], [if-else], [%], [вивести [x]], [вивести "⭐"]
```

Класичний interview-puzzle спрощений для 8-річки. **Дитина 9-10 років реально буде в захваті** (це ж справжня програмістська задача).

### Приклад типу задачі В — truth-table mystery (Day 8)

```
Задача: «Прогнозуй що виведе ця програма для x=7»

Програма (показана дитині, вона не пише, а ЧИТАЄ):
set x = 7
if (x > 3) AND NOT (x = 7)
  вивести "так"
else
  вивести "ні"

Дитина обирає: [так] [ні]
Після відповіді: програма виконується, видно правильну відповідь.
```

Це reverse-mode — дитина читає код, не пише. Розвиває code-reading skill, який критичний для будь-якого подальшого програмування. **Це власне ноу-хау цього треку — у Lightbot / Tynker / Module 1 reverse-mode фактично відсутній.**

## 4. Як використовувати ПРОЦЕДУРИ без візуальної сцени

### Приклад типу задачі А — створи власний блок

```
Задача: «Створи блок 'квадрат' що приймає число і виводить його квадрат.
        Виклич з 3, 5, 10.»

Очікуваний output: 9, 25, 100

Дитина створює:
define block "квадрат" with param (n):
  вивести n × n

call "квадрат" with 3
call "квадрат" with 5
call "квадрат" with 10
```

Метакогніція: «я зробив свою команду». Це фундаментальне перевертання — досі дитина ВИКОРИСТОВУВАЛА готові блоки, тепер вона ЇХ ТВОРИТЬ.

### Приклад типу задачі Б — багаторазовий виклик з різними параметрами

```
Задача: «Створи блок 'кутник(n)' що виводить ⭐-трикутник висотою n.
        Виклич для висот 3, 5, 7.»

Output: 3 трикутника один за одним (різного розміру)
```

Composition: блок із Day 4 (⭐-трикутник) перетворюється на reusable procedure. Дитина бачить як один абстрактний інструмент масштабується.

### Приклад типу задачі В — bonus рекурсія (Day 9 для прудких)

```
Задача: «Створи блок 'countdown(n)' що виводить n, n-1, n-2, ..., 1.
        БЕЗ використання repeat.»

Підказка: блок може викликати сам себе.

Очікуваний output для countdown(5): 5, 4, 3, 2, 1

define block "countdown" with param (n):
  if n > 0
    вивести n
    call "countdown" with (n - 1)
```

Це high-skill task. 70% 8-річок не доберуться, 30% доберуться з допомогою — і це буде їхній «aha-moment» який пам'ятатимуть. Опційно, не required для проходу.

## 5. Кастомні блоки які варто придумати

Із поточного `tasks.json` Module 1 переносимо тільки: жодного, бо стара бібліотека (`move_*`, `set_direction`) — це stage-блоки. Code-puzzle вимагає **нової повністю бібліотеки**.

**Пропоную 5 ключових кастомних блоків:**

### 5.1. `[вивести [value]]` — універсальний output
- Приймає: число, рядок, true/false, шаблон
- Авто-форматує: числа справа, рядки зліва, true/false з emoji
- Це наш дзеркальний `pencil_draw` з Module 1 — головна action-команда
- **Без цього блоку трек не існує**

### 5.2. `[⭐ × n]` — string multiply
- Приймає число, повертає рядок з n зірочок
- Дозволяє швидко робити патерни (трикутники, лінії, gradients)
- Замінює моторно-візуальну насолоду рухом — на статичну візуальну насолоду фігур
- **Альтернатива:** `[repeat (вивести ⭐)]` — багатословніше, але без кастомного блоку

### 5.3. `[ділиться на N?]` — predicate
- Спрощений modulo для 8-річки яка ще не вивчила знак `%`
- Повертає true/false
- Critical для Day 7 (FizzBuzz-style фільтри)
- Без нього треба пояснювати `mod 5 = 0` що для 8 років складно

### 5.4. `[random від N до M]` — randomness
- Повертає випадкове число
- Дозволяє: ігрові механіки, симуляції, лотерея на Day 10
- Це **єдиний non-deterministic блок** — потребує осторожного introduction («іноді одне, іноді інше»)

### 5.5. `[вивести [text] у [колір]]` — color-output
- Розширення базового output: text з кольором (5-6 пресет-кольорів)
- Дозволяє візуалізувати: червоне=fail/big, зелене=success/small, тощо
- Найголовніше — **візуальна різноманітність output box'у** без анімації stage
- Опційно, але різко підвищує перцептивну привабливість

**Не запроваджуємо:**
- `[обчислити]` / `[execute]` — це implicit, дитина не повинна викликати execution вручну (є кнопка Run)
- `[input from user]` — Phase 0 уникає inputs runtime, бо це лагає на mobile + потребує клавіатури
- `[wait N seconds]` — є у Module 1, тут зайве (немає анімації яку треба синхронізувати)

## 6. Чи зможе утримати дитину 8-10 без візуалу?

**Моя відповідь: ТАК, з 5 умовами.** Аргументація pro/contra нижче.

### Pro (підстава для «так»)

1. **8-10 років — вікове перетин раціональної мотивації.** На відміну від 6-7-річок які потребують animated rewards, 8-10 уже сприймають **інтелектуальну перемогу** як emotional payoff. Це підтверджують успіх Brilliant Junior, Khan Academy Kids math puzzles, Sudoku for kids — всі ці продукти БЕЗ персонажів тримають audience.

2. **Output as visible result — це і є наша сцена.** Якщо output box з'являється не одномоментно а **анімовано** (fade-in кожного елементу за 100-200мс, з тиком звуку) — це теж візуальна нагорода, просто інша. Аналог: progress bar у завантаженні — без персонажа, але дитина дивиться.

3. **Constraint puzzles + leaderboard = виклик.** «Знайди рішення за 4 блоки» — це той самий dopamine що Sudoku. Якщо додати **глобальний leaderboard коротших рішень** (як вже є в Module 1) — це додає competitive layer.

4. **Reverse-mode (читання коду) — це майже-magic.** На Day 7-8 ми вводимо tasks типу «спрогнозуй вивід». Це activates той самий mental loop що любителі дитячих логічних загадок (Smartivki, MENSA Junior). У Module 1 цього **немає взагалі**.

5. **AI-наставник Олексій залишається.** Він говорить з дитиною про код, питає «що далі робитиме програма?», робить wow-реакції на правильні рішення. Це **половина emotional bandwidth** Кодомандри — і вона не міняється.

### Contra (ризики «ні»)

1. **Без анімованого характеру втрачаємо identification.** Pixel-котик з Module 1 — це **аватар** дитини. У code-puzzle її аватар — це власне її програма. Це абстрактніше. **Дитина 8 років з низькою абстрактністю ризикує не залучитись.**

2. **Output box може здатися «школою».** Якщо UI viewport виглядає як TextEdit з числами — асоціація школа/контрольна. Треба активний UI/UX напрямок: яскраві кольори output, fonts, sound effects, emoji-enrichment.

3. **Math literacy — bottleneck.** Якщо дитина 8 років ще не впевнена у множенні / ділення / змінних з шкільної програми — вона спіткнеться на Day 2-5. Module 1 цього не потребує. **Висновок:** до 8.5+ років і успішним 2-3 класом — більш безпечно.

4. **Reading load більший.** Output має текстові підписи; задачі — текст. 8-річка з низькою grade у читанні буде borderline. TTS компенсує (Кодомандри має voice mentor) але це додаткове навантаження.

5. **Без stage — складніше debug.** У Module 1 коли Pixel зупинився не там — видно ДЕ. У code-puzzle коли output 14 замість 10 — дитина має ВЕСЬ код перечитувати щоб знайти помилку. **Потрібен step-by-step trace mode** (підсвітка наступного блоку, який щойно виконався + value у visible variables panel).

### 5 умов щоб «так» спрацювало

| # | Умова | Чому критична |
|---|---|---|
| 1 | **Output box має емоційну поведінку** (fade-in, ticks, color, emoji) | Замінює рух Pixel-а як visual reward |
| 2 | **Step-by-step trace mode** при перегляді результату («дивись як я виконую»: блок підсвічується, value змінюється) | Заміна video-debugging stage'у; без цього 50% дітей загубляться при першій помилці |
| 3 | **AI-наставник Олексій активний як у Module 1** — реагує на код, хвалить, підказує | Половина мотивації Кодомандри |
| 4 | **Leaderboard коротших рішень** + ⭐ за efficiency | Competitive driver. Власне Code-puzzle стає grippy |
| 5 | **Цільова аудиторія звужена до 8.5-10** (тобто 3-4 клас УА), не 8-10 широко | Математично-readable bottleneck. 8 років молодший може бути fail |

## 7. Найкрихкіше припущення цієї концепції

**Припущення:** Output-як-візуал (з fade-in, emoji-патернами, color-output) психологічно достатньо engaging для 8-10-річки, щоб замінити анімований Pixel-character.

**Чому це крихко:**

1. **Немає прямого емпіричного benchmark'у в UA-сегменті.** Усі дитячі code-puzzle продукти у нашому competitive landscape (Lightbot, CodeSpark, Tynker) — для англомовного ринку. UA-діти 8-10 з UA-language preference у нас — це **новий behavioral сегмент**.

2. **Output без анімації = «школа»; output з анімацією = «гра».** Тонка межа. Якщо UI/UX не доведений до рівня **«output виглядає як міні-сцена»** (анімація появи, sounds, colors) — асоціація школи переможе і ми втратимо 70% retention за 3-й тиждень.

3. **Step-by-step trace mode — недокументована функціональність на ранній спеці.** Я її передбачив у §6 як необхідну, але вона тягне за собою runtime instrumentation, value-history capture, animated highlights — це **половина obraz'у складності якої ми ХОТІЛИ позбутись.** Тут може бути circular dependency: ми хотіли простіше, а для рятування engagement довелось ускладнитись.

4. **Reverse-mode (Day 7-8 mystery puzzles) — не перевірено емпірично.** Я ставлю гіпотезу що reading code так само захоплююче як writing, але це **emperic claim** без UA-data. У англомовному edu є research на mid-school (11-14 років) що це працює. Для 8-10 — гіпотеза.

**Мітигація гіпотези:**

- **Step 1: bare prototype на 3 задачах** (Day 1 + Day 4 + Day 7) — без AI-mentor, без leaderboard, без полірованого UI. Дати 5-7 дітям 8-10 років по 15 хв «потикатись». Зафіксувати: чи фокус тримається ≥10 хв? Чи задають питання? Чи запитують ще завдань?

- **Step 2 (якщо Step 1 позитивний):** додати animated output + AI-mentor бот → ще 5-7 дітей × 30 хв. Зафіксувати: чи доходять до Day 4 (repeat)? Чи фрустрація на Day 7?

- **Step 3 (якщо Step 2 позитивний):** повний 10-денний прохід з 3-5 дітьми → baseline retention метрика.

**Якщо Step 1 fail** (діти кидають за 5 хв) — концепцію закриваємо без додаткової роботи. Module 1 + Lightbot-grid compromise (з попереднього концепту) залишається як основна еволюція.

## Висновок для рішення founder'а

**Рекомендація:** Робити Spike-прототип Day 1 + Day 4 + Day 7 (3 завдання). Не повний 10-денний курс. Виявити чи 5 дітей 8-10 років тримають увагу хоча б 10 хвилин чисто на output без stage.

**Якщо Spike позитивний:** code-puzzle стає **другим продуктовим треком** Кодомандри для 8-10 років. Module 1 заморожується в release-mode для 6-7. Один stack — два surfaces.

## Додатки

### A. Чому я обрав 10 днів а не 7

7 днів недостатньо щоб провести всі 7 концепцій (sequence, ops, repeat, var, if, logic-ops, procedures). Без consolidation-днів темп ламає принцип Phase 0 «1 concept/day max». З 10 днями маємо: 6 нових концепцій + 2 consolidation + 1 finale + 1 buffer/wow-day. Це **той самий ритм що Module 1** — не reinvent wheel.

### B. Зв'язок з sister-проектом quiz/

Concept у [`2026-06-14-code-puzzle-track-concept.md`](https://bajka.pp.ua/notes/phase0/reports/2026-06-14-code-puzzle-track-concept/) Appendix B описує можливість «один infrastructure stack — три product surfaces». Цей план робить це конкретним:

- **Math quiz** (quiz/) для дітей 7-12 — закриває арифметику/пропорції/частку через варіації-чисел drill
- **Code-puzzle** (новий трек) для 8-10 — закриває algorithmic thinking через output-based блоки
- **Module 1** (поточний Phase 0) для 6-7 — закриває первинне знайомство через візуальну стейдж

Дитина, яка пройде всі три треки до 11 років — отримає **повний фундамент**: математична автоматика, алгоритмічне мислення, візуальне програмне розуміння.
